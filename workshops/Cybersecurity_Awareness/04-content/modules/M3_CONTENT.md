# M3 content script

## SL23: A message that fits your work
Time: 12:00–12:05 (5 minutes). Layout: email. Evidence: fictional.
Objective: Identify the requested action

Screen copy:
- Who is asking?
- What would I authorise or disclose?
- How can I verify outside this message?

Evidence to create: Meeting, benefits and document invitations.
Interaction: Ask which action creates risk.
Reveal: Use context, action and independent route together.
Facilitator notes: Do not claim most breaches start with spear phishing.
Sources: S10, S11

## SL24: The sender behind the display name
Time: 12:05–12:12 (7 minutes). Layout: email. Evidence: fictional.
Objective: Inspect sender without treating it as conclusive

Screen copy:
- Expand the sender.
- Check the full address and reply destination.

Evidence to create: Manager display name with a different reserved .example address.
Interaction: Toggle sender details.
Reveal: A mismatch may be a clue; a match still needs request verification.
Facilitator notes: Explain sender spoofing, lookalike domains and compromised accounts in notes, not as a protocol lecture.
Sources: S10

## SL25: The destination behind the label
Time: 12:12–12:17 (5 minutes). Layout: browser. Evidence: fictional.
Objective: Read displayed destinations safely

Screen copy:
- Preview without opening.
- Find the actual hostname.

Evidence to create: Display https://login.company.example.attacker.test/review as inert text.
Interaction: Highlight hostname parts after vote.
Reveal: Hostname ends with attacker.test.
Facilitator notes: Reserved .test domain. Genuine hosting and redirects can also be abused. Never navigate.
Sources: S10

## SL26: A polished message can still deceive
Time: 12:17–12:23 (6 minutes). Layout: comparison. Evidence: fictional.
Objective: Avoid grammar-based trust

Screen copy:
- Professional writing and a familiar logo do not establish intent.

Evidence to create: Two polished messages: legitimate HR notice and deceptive approval request.
Interaction: Ask what business verification each requires.
Reveal: Focus on the action and context.
Facilitator notes: AI can improve lure writing, but do not label a sample AI-generated without evidence.
Sources: S11

## SL27: The same request on a phone
Time: 12:23–12:29 (6 minutes). Layout: mobile. Evidence: fictional.
Objective: Inspect compressed mobile evidence

Screen copy:
- The screen shows less detail.
- Open the known application directly.

Evidence to create: SMS or WhatsApp notification requesting account review.
Interaction: Compare desktop/mobile sender visibility.
Reveal: Use the known service and report suspicious requests.
Facilitator notes: Do not suggest mobile is inherently unsafe.
Sources: S5, S3

## SL28: A QR code moves the request
Time: 12:29–12:35 (6 minutes). Layout: qr. Evidence: fictional.
Objective: Treat QR as a route requiring verification

Screen copy:
- Where would this code take you?
- Did you initiate this sign-in or linking action?

Evidence to create: Mock account-security email with an inert QR tile.
Interaction: Reveal destination in the deck, not via phone scan.
Reveal: Use the known portal instead of an unsolicited request.
Facilitator notes: No functional login/linking QR. Distinguish URL phishing from device-linking later.
Sources: S3

## SL29: A shared file is still a request
Time: 12:35–12:41 (6 minutes). Layout: email. Evidence: fictional.
Objective: Assess document and attachment pretexts

Screen copy:
- Branding and file format do not establish safety.

Evidence to create: PDF/HTML/SVG file card and shared-document invitation.
Interaction: Select inspection cards; no file opens.
Reveal: Verify the sharing context before unexpected login/download.
Facilitator notes: Keep attachment behaviour inert. File formats are examples, not automatic malicious classifications.
Sources: S3, S11

## SL30: Would you approve this?
Time: 12:41–12:49 (8 minutes). Layout: exercise. Evidence: fictional.
Objective: Apply process to both genuine and deceptive requests

Screen copy:
- Proceed, verify or report?
- Explain the next action.

Evidence to create: Four cards: genuine bank change, compromised colleague, genuine portal IT notice, fake manager exception.
Interaction: Table groups select an action for each.
Reveal: Independent verification may be right for genuine sensitive requests too.
Facilitator notes: Use EXERCISES.md answer key. Score process, not number of messages called malicious.
Sources: S7, S20

## SL31: The signals that do not prove safety
Time: 12:49–12:56 (7 minutes). Layout: reveal. Evidence: fictional.
Objective: Challenge misleading assurances

Screen copy:
- Familiar logo
- Known sender
- HTTPS or no email warning

Evidence to create: Three claimed assurances plus optional fluent wording and MFA.
Interaction: Reveal what each signal establishes and its limit.
Reveal: Appearance, delivery and authentication do not validate the business request.
Facilitator notes: Do not imply HTTPS is useless. It protects a connection to the destination.
Sources: S11, S12

## SL32: Your verification route
Time: 12:56–13:00 (4 minutes). Layout: response. Evidence: guidance.
Objective: Consolidate independent verification

Screen copy:
- Use a known app, saved address or established contact.
- Verify sensitive changes before acting.

Evidence to create: Aina receives another document invitation.
Interaction: Ask each table to name its route.
Reveal: Use the organisation’s actual process.
Facilitator notes: This is a course summary, not an official mnemonic.
Sources: S7, S20
