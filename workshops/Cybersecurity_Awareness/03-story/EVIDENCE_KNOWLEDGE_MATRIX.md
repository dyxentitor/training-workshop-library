# Evidence and knowledge boundaries

| Point | Known to the learner | Unknown until later | Allowed conclusion |
|---|---|---|---|
| Opening email | Expected invoice, changed details, deadline | Who controls sender/account; genuine bank change | Verify independently |
| Opening chat | Display name and pressure | Ravi's actual involvement | Maintain process; verify identity |
| Callback reveal | Supplier and Ravi deny requests | Full compromise mechanism | Hold action and report; IT investigates |
| Profile example | Public details and copied appearance | Who controls either profile | Established contact check |
| Code prompt | A supplied code and genuine-looking service | Initiating session/device ownership | Do not authorise an unfamiliar session |
| Tabletop T2 | Aina reports entering a code | Whether T3 is causally linked | Urgent report; access review |
| Tabletop T3/T4 | New bank request and unsolicited support | Account/operator attribution | Separate facts, hypotheses and next actions |

Never award points for claiming certainty beyond the evidence. The trainer's reveal can provide new facts, but should not retrospectively call those facts obvious clues. A source-backed attack family is not proof of the fictional scenario's full causal mechanism.
